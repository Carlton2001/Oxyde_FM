# System integration

What lets Oxyde stand in for the system's file manager and for the Open and Save dialogs of other applications, on Linux and on Windows. Installing and packaging: [Windows distribution](../guides/distribution.md), [Linux distribution](../guides/linux-distribution.md). Security: [code loaded by other applications](../security/status.md#answering-other-applications-dialogs-optional).

## Settings

Both options are off by default and sit in the **System integration** submenu of Preferences (`ui/components/settings/integration.rs`): a checkbox each, its explanation shown below, and only the options the system allows; the submenu's row is hidden when it allows none. `ui/app/folder_handler.rs` drives the default file manager, `ui/app/file_chooser/setting.rs` (`Platform::chooses_files`) the dialogs.

## One instance per session

Whatever starts Oxyde, a session has one: a later launch hands its locations to the running Oxyde, which opens them as tabs and comes forward (`ui/app/instance.rs`).

### Instance on Linux

`platform/linux_instance.rs`. Before any window, Oxyde asks the session bus for `io.github.Carlton2001.Oxyde` (`.Devel` for debug builds, so a `cargo run` never talks to an installed copy) with `DoNotQueue`. The first process keeps it and serves `io.github.Carlton2001.Oxyde1.Open(as locations, s token)` at `/io/github/Carlton2001/Oxyde`; it restores the saved session and adds each received location as a new tab. A later launch calls `Open` with `XDG_ACTIVATION_TOKEN` (or `DESKTOP_STARTUP_ID`) and exits before GPUI starts; the running one adds the tabs and presents the token through `Window::activate_window_with_token`, a local GPUI patch (`vendor/gpui_linux/README.oxyde.md`), so Mutter and KWin bring it forward. Without a session bus, or if the running Oxyde does not answer within five seconds, the process runs alone as before: it shows only the received locations and leaves the saved session untouched.

### Instance on Windows

`platform/windows_instance.rs`. The first process owns the only instance of a named pipe (`\\.\pipe\Oxyde.Instance.<Release|Devel>[.Elevated].<session>.<hash of the storage folder>`), so an installed copy, a portable copy and a debug build keep to themselves. The pipe is created as the user's own, writable by the user's processes at medium integrity, whatever rights Oxyde runs with. An Oxyde run as administrator owns the `.Elevated` name and does not give way to one that is not; the launcher tries the name of its own rights, then the other, so a folder opens in the Oxyde that runs. A later launch, or the launcher, checks that the pipe's owner is its own account, lets the owner come forward with `AllowSetForegroundWindow`, writes its locations and ends; the running Oxyde adds a tab for each and activates its window. Without locations, the window only comes forward. When the pipe cannot be reached, a launch of Oxyde runs alone and shows only what it received. As it starts to quit, Oxyde closes the pipe (`Platform::release_instance`, from the GPUI quit hook): its last saves can take seconds, during which a folder handed over would be taken and never shown; the next launch finds no pipe and starts an Oxyde of its own.

**Received folders** (`platform/windows_startup.rs`): arguments that are existing folders open as tabs, a file stands for its folder, `"C:\"` (received as `C:"`) is the drive's root; switches and Shell names (`::{CLSID}`, `shell:`) are ignored.

## Default file manager

### Folders on Linux

GIO does the work, in `platform/linux_gio/applications.rs`. Checked, the option:

- makes Oxyde the default for `inode/directory` in the user's `mimeapps.list` and keeps the application it replaced in `folder_handler_before`; off, it gives folders back to that application, or resets the user's folder associations when it is gone;
- writes `$XDG_DATA_HOME/dbus-1/services/io.github.Carlton2001.Oxyde.FileManager1.service`, whose `Exec` is the desktop entry's program, asks the bus to reload, and requests `org.freedesktop.FileManager1` with `AllowReplacement`. User service files take precedence over `/usr/share`, so the bus starts Oxyde rather than Nautilus; a program already holding the name keeps it, and Oxyde waits in the queue. Off, the file is removed and the name released.

At each start, a thread makes the service file and the name follow the folder default, which `install.sh --set-default` or another program may have changed. `ShowFolders` opens tabs, `ShowItems` opens one tab per folder with its items selected, `ShowItemProperties` opens Properties. The switch is shown only when GIO finds the desktop entry. `install.sh --uninstall` removes the service file.

Limits: another program's user service file for `org.freedesktop.FileManager1` (Strata writes one) competes with Oxyde's, and the bus keeps whichever it reads first; the dock's Files icon stays the desktop's; a non-UTF-8 name is ignored.

### Folders on Windows

The registry work is in `platform/windows_folder_handler.rs`. Everything is written for the user under `HKCU\Software\Classes`, without elevation, and the Shell is told with `SHChangeNotify(SHCNE_ASSOCCHANGED)`, so the change applies to the next folder opened. The commands name `oxyde-folder-launcher.exe`, shipped next to the main executable; the option is not listed when it is missing, nor in a portable copy: deleted or moved, that copy would leave folders to a launcher that is gone, with nothing left to give them back. A portable copy that already is the default still lists the option, to turn it off. Checked, the option:

- sets the default verb of `Directory` and `Drive` to `open` (the system's is `none`, which leaves the choice to `Folder`) and their `shell\open\command` to `"<launcher>" "%V"`, with an empty `DelegateExecute`;
- sets `CLSID\{52205fd8-5dfb-447d-801a-d0b52f2e83e1}\shell\opennewwindow\command`, the command behind Win+E, to the launcher, with an empty `DelegateExecute`;
- keeps the user's values it replaced, as JSON in `folder_handler_before`. Off, they are written back, values that did not exist are removed and keys left empty are deleted, which gives the system's values back. Kept values are not written back when a command among them runs a program that is no longer there, such as a file manager uninstalled since: the system's values are given back instead.

`Folder` is not touched: Control Panel, the Recycle Bin and the other namespace folders stay Explorer's. The option reads as checked when the merged `HKCR\Directory` names this copy's launcher, so a copy moved elsewhere reads as unchecked and can be chosen again; the values kept at the first change are then reused. Files (files-community) registers a launcher the same way, on `Folder`.

**The launcher** (`src/bin/oxyde-folder-launcher.rs`, `platform/windows_folder_launcher.rs`) is what Explorer starts for every folder opened, its own windows included: a windowed program of about 1 MB, without console, interface or runtime, with the workers' icon. In order, it leaves the folder to the Explorer tab it came from, hands it to the running Oxyde over the instance pipe, or starts `Oxyde_FM.exe` (`oxyde.exe` in a Cargo build) on it; unless Explorer kept the folder, it then stays up to ten seconds for a file to show in it (below). Without a folder (Win+E), the running Oxyde comes forward or one starts.

**Explorer keeps its own windows** (`platform/windows_explorer_browse.rs`). With the verb replaced, Explorer runs it for a folder opened in its own list instead of browsing in place. When Explorer is the launcher's parent process, the launcher therefore looks for the tab the folder came from and asks it to browse there (`IShellWindows`, `IShellBrowser::BrowseObject`). Opening a folder in a list selects it, so the tab is an active one where the folder is selected, itself or as the target of a selected shortcut: the foreground window's, else the only one. Selected with other items, the folder gets an Explorer window of its own (`explorer.exe <folder>`, which does not go through the verb), as Explorer gives each folder of a selection. From the desktop, the taskbar or another program, the folder is Oxyde's, as when Explorer does not answer; so is one Explorer opens for the Run dialog, the Start menu or a jump list, selected in no tab, whatever Explorer window is in the foreground.

**Show in folder** (`platform/windows_shell_window.rs`). A program that shows a file in its folder calls `SHOpenFolderAndSelectItems`: the Shell opens the folder, which starts the launcher, then looks in `IShellWindows` for the window showing that folder and asks its view to select the file. As Files' launcher does, the launcher registers a window nobody sees as showing the folder (`RegisterPending`, `Register`, `OnNavigate`), an `IWebBrowserApp` whose `IShellView::SelectItem` only notes the items. The Shell matches a window by the identifier list of its folder, compared as written, and a folder of the user's profile has two: through the drive, as `ILCreateFromPath` writes it (Firefox, Zed), and through the known folder it is in, as `SHParseDisplayName` does (Explorer, Task Manager). The launcher therefore registers one window for each; under the other list a caller finds nothing, waits twenty seconds and gives up with `E_ABORT`. The folder is handed to Oxyde at once, without waiting for a selection; the launcher then answers the Shell for ten seconds at most, or until 20 ms after the last item, and hands the items over the pipe (`oxyde-select 1`, where folders are `oxyde-open 1`), waiting up to twenty seconds for an Oxyde it just started. Oxyde selects them in the active tab when it shows their folder, as it does after the folder was just opened, and in a new tab otherwise. A second request for the same folder within those seconds finds the launcher's window and selects through it. `the_file_a_program_shows_in_the_folder_is_the_selection` checks the exchange with the real Shell, for a caller of each kind; it is ignored by default, as it needs a desktop session.

Limits: a program that starts `explorer.exe` itself (`explorer.exe /select,<file>`, as NanaZip appears to) opens Explorer, which no association can prevent. The Open and Save dialogs are a separate, experimental option ([below](#windows-dialogs-experimental)).

## Open and Save dialogs

### The chooser window

`ui/app/file_chooser/` is one window for both systems. It answers a `FileChooserRequest`, the portal's request: the option names below are the portal's, and Windows translates its dialog's settings into them. The window lists real folders off the UI thread, filtered and sorted there too. Its pieces are copies of the main window's, adapted to choosing; what they computed word for word (crumb motion, type-ahead, arrows, column measurement) is the main window's own code: the sidebar (resizable; its places, drives and the volumes to mount on a click follow the main window's; drives unfold their folder tree with the main sidebar's folder rows, `sidebar/folder_row.rs`: the chevron or a double press unfolds, a press opens, folders are listed off the UI thread from those the main window already knows, and with its path tracking the tree unfolds to the folder open and centers it; what unfolds there leaves the main sidebar alone), the navigation bar (Back, Forward, Up, New folder, crumbs with their folder menus and a right-click Copy path, the path edited on a double click or in the blank area, also with Ctrl+L or `/` and `~` in the list; a typed folder opens, a typed file is chosen), the quick search control as a name filter (Ctrl+F; its arrows move the selection), the measured Name, Type, Size, Permissions (when the main window shows it) and Modified columns sorted from their headers, the grid with the main window's thumbnails, the status bar with its view switch, the scrollbars (a press beside the thumb moves it there, menus' thumbs included) and the button back to the start beside the entries' rail, tooltips under the main window's rules, hidden files (Ctrl+H), Refresh (F5), Backspace and type-ahead selection. Up stays at the root, disabled. New folder (Ctrl+Shift+N) creates the first free "New folder" off the UI thread, recorded in the main window's history so its Undo removes it, then edits its name in place until Enter, a click elsewhere or Esc; a refused name frames the field in red and shakes it, as in the main window. Entries' tooltips go while a selection rectangle is drawn. Everything the application asks sits below the entries, between borders, on the inactive panels' background: a form of rows whose labels share one column measured in the language shown (Name, Type, the choices' menus, then their checkboxes on the controls' edge). Below it, the secondary windows' usual footer holds only Cancel and the button. More than three menus sit side by side where the width allows; past a third of the window the form scrolls with the shared scrollbar. Tab and Shift+Tab move the keyboard from the entries through the footer's controls in that order (then Cancel, the button when enabled) and back, scrolling the form to the control reached, with the main window's focus ring; Enter or Space presses a button or a checkbox, Space, Enter or Down opens a menu, and Esc cancels. With `multiple`, Ctrl, Shift and Ctrl+Shift presses, Shift with the arrows, Ctrl+A, Ctrl+Shift+A and the selection rectangle drawn from beside the entries (Shift adds, Ctrl toggles, the list scrolls near its edges) select several entries as in the main window; Enter opens a single entry and chooses several; the button chooses the files selected, or opens a single folder selected. With `directory`, only folders are listed, a typed file is refused, and the button ("Select") chooses the folders selected, else the folder open. `filters` (`a(sa(us))`: shell patterns that keep case, as GTK's, and MIME types matched through the shared MIME database's aliases and subclasses, `image/*` by media) are offered in a Type menu of that form; `current_filter` is shown first, alone when no list comes with it, added when the list lacks it; folders are always listed. Files' MIME types are read with the listing, only when a filter names one. `current_folder` (`ay`) opens first when it is a folder. Its view, sort, sidebar width and last folder are kept in the preferences as `file_chooser_options`, and the next window starts there unless the application suggests a folder. `SaveFile` adds a Name field at the top of that form, which has the keyboard first with the stem of `current_name` (or of `current_file`, the file saved again, whose folder then opens first) selected; a file pressed or reached in the list gives its name, and a double press or Enter on it saves over it. The name is typed relative to the folder open, `~`, `..` and subfolders included, as is a path typed in the navigation bar: a folder opens and the name is cleared, an existing file (or link) is replaced once a prompt confirms it, a free name in an existing folder is chosen, and anything else shakes the field in red. Without a name, the button ("Save") opens the single folder selected. The prompt is a `WindowKind::Dialog` window parented to the chooser, which takes no input meanwhile (Cancel first, Tab, Enter or Space, Esc); type filters apply to the list as when opening, and changing them leaves the name's extension alone, as GTK 4 does. `SaveFiles` chooses a folder as `directory` does; its `files` (`aay`, only their last component kept) go in the folder chosen, those already there replaced once the same prompt, listing the first three, confirms it. `choices` (`a(ssa(ss)s)`) sit in that form after the type filter: a label and a menu for those with answers, then a row of checkboxes for the others (`"true"` or `"false"`), an answer given first that is not offered becoming the first one; they go back as `choices` (`a(ss)`) with any answer, opening included.

Some requests carry `FileChooserExtras`, what the portal cannot say and Windows dialogs can (`additions.rs`): their own labels for Name and Cancel; text fields, labeled rows after the menus whose texts go back with the choices on one line; notes, muted rows after the checkboxes; controls shown but disabled (a faded menu, checkbox or read-only field, left out of Tab); and the ways to accept, a menu behind a chevron beside the button whose item picked accepts (the button stands for the last one picked) and goes back as a choice. They can also hide the pinned folders, add folders to the places (before Home or after the pins, named by their folder, with a folder icon), show hidden files, hold the button until the user moved among folders, pressed in the pane, moved in the list with the keyboard or typed a name, give a name saved under the shown filter that filter's extension when the filter does not show it, refuse a read-only file to save over (the field shakes), and save over a file without the prompt. A `client` key, the portal's `app_id` or the Windows program with its client GUID, keeps the folder each application last chose in (the 32 latest, in `file_chooser_options`); the window then opens on the application's folder, else that one, else its default folder, else the last one.

### The Linux portal

`platform/linux_portal.rs` and `linux_portal/`. Applications that ask through `xdg-desktop-portal` (Flatpak, Firefox, Chrome, recent Electron) get Oxyde as their file chooser, as Strata does. Checked in the System integration submenu (off by default, listed only when the portal and a program to start exist), the option:

- writes `$XDG_DATA_HOME/xdg-desktop-portal/portals/oxyde.portal` (`DBusName=org.freedesktop.impl.portal.desktop.oxyde`, `Interfaces=org.freedesktop.impl.portal.FileChooser;`) and `$XDG_DATA_HOME/dbus-1/services/org.freedesktop.impl.portal.desktop.oxyde.service`, whose `Exec` is the desktop entry's program with `--portal`; debug builds use `oxyde-devel` and `….oxyde.Devel`, and the build itself as program;
- puts `oxyde` first in the `org.freedesktop.impl.portal.FileChooser` line of the user's `$XDG_CONFIG_HOME/xdg-desktop-portal/<desktop>-portals.conf` (or the `portals.conf` they have), the portals it named staying after it as fallback; without such a line, it adds one, marked `# Added by Oxyde for its file chooser.`, with the `default` portals after `oxyde`; without a file of the user's, it writes a copy of the configuration the portal read, marked `# Written by Oxyde from <path>`. Links are written through. Off, removing `oxyde` gives back the line as it was, the marked line goes with its comment, and the copy goes when nothing else changed in it;
- asks the bus to reload, requests the name, and restarts `xdg-desktop-portal.service` through systemd, as the portal reads its files only at startup.

The running Oxyde serves `org.freedesktop.impl.portal.FileChooser` at `/org/freedesktop/portal/desktop` on its instance connection; at each start, while the configuration names it first, it writes the two files again if an update changed them and requests the name. When nothing serves the name, the bus starts `oxyde --portal`: that process becomes the session's Oxyde without a main window, which a later launch opens on its tabs; if an Oxyde already runs, it calls `ServeFileChooser` on it and exits, and the running one takes the name. `OpenFile`, `SaveFile` and `SaveFiles` export an `org.freedesktop.impl.portal.Request` at the call's handle; `Close` closes the window unanswered (response 2), Cancel, Esc or the window's close button answer 1, and a choice 0 with the `file://` URIs chosen and, when the application gave filters, the `current_filter` shown, and its `choices` answered. `parent_window` makes the window a modal dialog of the application's, placed by the desktop (GNOME attaches it to its parent, as its own file dialogs): `x11:<hex id>` sets `WM_TRANSIENT_FOR`, `_NET_WM_WINDOW_TYPE_DIALOG` and `_NET_WM_STATE_MODAL` before the window maps, `wayland:<handle>` imports the application's exported toplevel through `zxdg_importer_v2` (v1 when the compositor lacks it), parents to it with `set_parent_of` and makes the window modal with `xdg_dialog_v1`. GPUI does it from `WindowOptions::foreign_parent`, a patch of `vendor/gpui` and `vendor/gpui_linux`. An empty handle, a compositor without xdg-foreign or a handle of the other protocol (an application running through XWayland while Oxyde runs on Wayland, or the reverse) leaves an independent window; the saved position serves only that one.

Once chosen, every portal dialog depends on Oxyde: the portal waits for its backend without a limit and applies its own fallback only to a backend that is missing, not to one that fails. Oxyde therefore hands a call to the next portal of the line (its `.portal` file gives the bus name; same arguments, on a connection without Oxyde's five-second limit, `Close` included) whenever its window cannot answer: the interface has gone, the window failed to open, it has not shown within 10 seconds (a start for the call included; a window coming later does not open), or the interface thread panics. The panic hook then releases the session's names (Oxyde's own and FileManager1, so that a launch starts a new Oxyde; the portal's stays, as the portal withdraws calls through it), hands on the calls waiting for a window and holds the process, its windows frozen, until they are answered. A start for the portal that ends before a window shows counts as failed (`oxyde-portal-starts` in Oxyde's cache folder, with the version): after two in a row, the next start opens no window, leaves the session's name free and relays every call until none came for 30 seconds; a window shown, Oxyde ending by itself or another version clears the count. When the portal that called leaves the bus (restarted, or the option changed), the window closes unanswered and a request handed on is withdrawn. Oxyde ends with its last window only once no call waits for an answer; at exit it gives the last replies two seconds and calls handed on the time the user takes there, after releasing the session's names. An Oxyde started for the portal that never gets a window ends after 30 seconds. A crash the process cannot see (a signal) leaves the application's dialog failed (response 2), and the next call starts a new Oxyde. `install.sh --uninstall` removes the two files and, when no system copy remains, takes `oxyde` out of the line the same way, then restarts the portal.

Applications that use their toolkit's own dialog without the portal keep it.

To show the chooser without another application, `scripts/show-file-chooser.sh` calls the running Oxyde's interface as the portal would (Open, several files, folders, filters, choices, a Save with many choices, Save, Save again, Save several), and prints the answer.

### Windows dialogs (experimental)

Listed as **Open and Save dialogs (experimental)**; checked, applications that ask for a file get [Oxyde's file chooser](#the-chooser-window) in place of the Windows dialog. Four pieces take part:

- **The library** `oxyde_file_dialog.dll` (`shell/oxyde-file-dialog`, a package of its own, about 300 KB, C runtime linked statically) is what applications load. It serves the two classes of the common item dialog, `CLSID_FileOpenDialog` and `CLSID_FileSaveDialog`, and gives each application the system's own dialog, created straight from `System32\comdlg32.dll`, inside a wrapper. Everything the application sets is passed on to the system's dialog, which stays ready to be shown. `Show` asks Oxyde for a plain dialog and shows the system's dialog in every other case: the application added a control Oxyde has nothing like (a menu or a push button, whose events come while the dialog is open, which the one-shot answer cannot carry), used `SetFilter`, `SetNavigationRoot` or `FOS_ALLNONSTORAGEITEMS`, it took from the system's dialog an interface the wrapper does not have (the undocumented `IFileDialogPrivate` of the older `GetOpenFileName` path, for instance), the application is Oxyde itself, Oxyde cannot be reached or shows no window within fifteen seconds, or anything fails. The application's visible combo boxes and radio button lists become menus in Oxyde's footer, its check buttons checkboxes and its edit boxes text fields, labeled by their own label, their visual group's or the text before them; a text naming none of them is a note, a disabled control shows disabled, and the open button's drop-down (`EnableOpenDropDown`) is the menu beside Oxyde's button. The answers are set back on the system's dialog, whose listeners are told of each change (an edit box's text is set silently, as typing tells none), before `OnFileOk`. The wrapper also passes on `SetFileNameLabel`, `SetCancelButtonLabel`, `AddPlace`, `SetClientGuid`, the folder the system's dialog would open (which it remembers for the application) apart from `SetFolder`'s, and the options `FOS_FORCESHOWHIDDEN`, `FOS_OVERWRITEPROMPT` (its absence), `FOS_STRICTFILETYPES`, `FOS_NOREADONLYRETURN` (saving only), `FOS_OKBUTTONNEEDSINTERACTION` and `FOS_HIDEPINNEDPLACES`; what is chosen in Oxyde goes to the recent documents unless `FOS_DONTADDTORECENT`. Not shown: the Save dialog's properties pane (`SetCollectedProperties`), and `ClearClientData` leaves Oxyde's remembered folder. While Oxyde is shown, the application's window is disabled and its messages keep being dispatched. The listeners' `OnFileOk` is called on the choice, and a refused choice is asked again. A shortcut chosen to be opened gives its target unless `FOS_NODEREFERENCELINKS` is set.
- **The launcher** (`platform/windows_file_dialog/relay.rs`): the library holds no protocol. It runs `oxyde-folder-launcher.exe --choose` with the request on its standard input, inheriting those two pipes and nothing else, and reads the answer on its standard output. The launcher creates a pipe for the answer (`\\.\pipe\Oxyde.Dialog.<pid>.<random>`, the user's own, as the instance pipe), hands its name and the request to the running Oxyde (`oxyde-choose 1` on the instance pipe), or starts `Oxyde_FM.exe --file-chooser`, which opens no main window and ends with the chooser. Ending with code 2 means "show the system's dialog". The library ends the launcher when the application calls `Close`.
- **Oxyde** (`platform/windows_file_dialog.rs`) turns the request into the `FileChooserRequest` of the portal, answers on the launcher's pipe (`shown`, then `ok` with the paths and the filter, or `cancel`) and closes the window unanswered when the launcher's process ends. The chooser is owned by the application's window, adds the extension of the shown filter (else the default one) to a name saved without one, and matches filters without regard to case.
- **The registration** (`platform/windows_file_dialog/registration.rs`): `InprocServer32` of the two classes under `HKCU\Software\Classes\CLSID`, pointing to the library, `ThreadingModel` `Apartment` as the system's. Unchecking removes the keys, which restores the machine's registration. Applications find the change at their next dialog; one that already loaded the library keeps it loaded until it ends.

Not covered, by design of Windows: applications run as administrator (COM ignores the user's classes for them), 32-bit applications (they read `Software\Classes\WOW6432Node`, where nothing is written, and would need a 32-bit library), packaged applications that pick files through the system's broker, and applications that draw their own dialog. An Oxyde run as administrator answers the applications of the user all the same.

**A registration that points nowhere would leave every application without a dialog**, since COM does not fall back to the machine's class. Hence: the option is offered only where the library is, next to the executable, and not in a portable copy, whose archive does not hold the library; the uninstaller withdraws the registration (`--restore-folder-handler`) before removing files; and Oxyde removes a registration to a copy of its library that is gone each time it reads the option. By hand: delete `HKCU\Software\Classes\CLSID\{DC1C5A9C-E88A-4DDE-A5A1-60F82A20AEF7}` and `{C0B4E2F3-BA21-4773-8DBA-335EC946EB8B}`.

**Updates.** The Setup replaces a library still loaded by renaming it: [distribution](../guides/distribution.md#system-integration).

**Antivirus and security products.** Registering a class of the system for the user so that other programs load one's library is the technique known as COM hijacking (MITRE ATT&CK T1546.015), which malware uses to persist and to run inside other processes. A security product cannot tell the intent from the registry alone, so this option can:

- raise an alert, or be reverted or blocked, when the keys are written, more likely so since the executables are not signed;
- have the library quarantined, which leaves the registration pointing nowhere (see above: applications then have no dialog until the keys are removed or Oxyde's settings are opened);
- be refused by applications that only load libraries signed by Microsoft or by themselves (browsers' sandboxed processes, some protected or anti-cheat software): the class then fails to load there, and such an application may show no dialog while the option is on;
- make Oxyde's library part of every application that shows a dialog: a fault in it is a fault of that application. It is kept small for that reason, starts no thread but the one reading the launcher's answer, catches its own panics in `Show` and falls back to the system's dialog.

The library writes nothing and contacts nothing but the launcher next to it. It is off by default, labelled experimental, and removed entirely by unchecking the option. Diagnostics: set `OXYDE_FILE_DIALOG_LOG` to a file path in the environment of an application, and the library appends what it was asked, what Oxyde answered and which interface made it leave the dialog to Windows. Files (files-community) replaces the dialogs the same way.

Tests: `shell/oxyde-file-dialog/tests/dialog.rs` loads the library as an application does, with a fake launcher, so nothing shows on screen (Open with several files, Save under a free name, folders, cancellation, a refused choice, the interfaces); `platform/windows_file_dialog/tests` answer requests over real pipes. The system's dialog being shown instead, and the registration itself, are checked by hand.

## Menus of folders and of the taskbar (Windows)

`ui/app/system_menus.rs` tells the platform what to list, at start and whenever the pinned folders or the default for folders change; the platform writes off the UI thread.

**Open in Oxyde** (`platform/windows_folder_handler/menu.rs`): a verb `Oxyde` of `Directory`, `Directory\Background` and `Drive` under `HKCU\Software\Classes`, labelled in the user's language, with Oxyde's icon, running `"Oxyde_FM.exe" "%V"`. Only the copy the Setup installed lists itself (its folder is the `InstallLocation` of `Uninstall\Oxyde.GPUI.Windows_is1`), and only while it is not the default for folders, when opening a folder already shows it in Oxyde; checking the option removes the verb, unchecking it writes it back, and the uninstaller removes it. No setting: it follows the default file manager option. A portable copy and a Cargo build never write it, so it can only be tried from a Setup. On Windows 11 a verb of the registry shows under **Show more options** (Shift+F10); the short menu only lists packaged applications, which Oxyde is not.

**Taskbar menu** (`platform/windows_jump_list.rs`): right-clicking Oxyde's taskbar button lists the pinned folders of the sidebar (Quick access), each opened as a tab, and a task **Run as administrator**. There is no list of recent folders, which Oxyde does not keep, and no new window, which panes replace. The task is a shortcut to `Oxyde_FM.exe --run-as-administrator`, which starts Oxyde again with the `runas` verb and ends: a shortcut cannot ask for elevation. The elevated Oxyde is an instance of its own ([instance on Windows](#instance-on-windows)). When the user turned off recently opened items in Start and jump lists (`Start_TrackDocs` 0), Windows refuses an application's categories with `E_ACCESSDENIED`; the folders are then listed as tasks above a separator. Folders the user removed from the menu are left out of the next list, as Windows requires. `the_shell_accepts_the_menu` writes a list under a test identity and deletes it; it is ignored by default, as it needs a desktop session.

**Application identity.** The list belongs to an `AppUserModelID`. The process takes `Oxyde.GPUI.Windows`, the one of the Setup's shortcuts, before its first window (`Platform::identify_process`), so the button, a pinned shortcut and the menu are the same however Oxyde was started; a debug build takes `Oxyde.GPUI.Windows.Devel`. A taskbar pin made from a window of an earlier version, which had no identity of its own, no longer matches and has to be pinned again.
